- **สรุปสั้น (2 ต.ค.):** **เขียนโค้ดรอบ "บัญชีนักเรียนระดับโรงเรียน ห้องประจำชั้นร่วม และเข้าสู่ระบบด้วย Google" (DESIGN §24) ครบ 5 build ทั้ง backend และ app แล้ว** บน branch `feat/school-accounts` (**ยังไม่ merge เข้า `main`**) นักเรียนหนึ่งคนมีบัญชีเดียวทั้งโรงเรียน รวมบัญชีที่ซ้ำได้ ห้องเก่าอ่านอย่างเดียว ครูประจำวิชาขอสอนห้องของครูประจำชั้น ทุก role เข้าสู่ระบบด้วย Google ได้ (ยังไม่ได้สร้าง project sign-in จริง) และนักเรียนหลายห้องเห็น "วิชาของฉัน" หน้าเดียว test ทุกชุดผ่านทั้ง SQLite และ MariaDB และ smoke ทั้งวงจรผ่าน 68 ขั้น รายละเอียดในหัวข้อ 2 และ 3 สิ่งที่ทีมต้องทำต่ออยู่ในหัวข้อ 6 (ข้อ 15–18)

### Phase 10: ข้อสอบและกระดาษคำตอบ (DESIGN §22, branch `feat/exams-gradebook`)

ข้อสอบคือการบ้านชนิด `exam` ใช้รายชื่อ คิวตรวจทาน การเผยแพร่ item analysis และ mastery เดิมได้ทั้งหมด **ทุกคำตอบเป็นการฝน ตรวจด้วยโค้ด ไม่ใช้ Gemini ตรวจ** Gemini ใช้เฉพาะอ่านไฟล์ข้อสอบของครู

| ส่วน | backend | app |
|---|---|---|
| สร้างข้อสอบ | ตอน (ปรนัย 2–6 ตัวเลือก, ถูก/ผิด, เติมตัวเลข), ข้อสูงสุด 200 ข้อ, เฉลยหลักชุดเดียว, **ชุดข้อสอบ ก–ง** สลับข้อและตัวเลือกในตอน (ล็อกเมื่อพิมพ์ครั้งแรก), วิธีตรวจ "ตรวจด้วยแอป" หรือ "ครูตรวจเอง" | หน้าแก้ข้อสอบ ตอน ข้อ ตารางเฉลย หน้าชุดข้อสอบ |
| เพิ่มข้อ | พิมพ์เอง, **อ่านไฟล์ข้อสอบด้วย Gemini ครั้งเดียว** (แคชทั้งโรงเรียน) ได้ข้อร่างที่ครูต้องอนุมัติ + ตัดภาพประกอบด้วย GD, คัดลอกข้อจากข้อสอบเดิมของตัวเอง | แนบไฟล์, ลากกรอบภาพประกอบ, คลังข้อ |
| พิมพ์ | เล่มข้อสอบต่อชุด, กระดาษคำตอบรายคน (QR `EVX1` มีลายเซ็น, ไม่เกิน 2 หน้า), กระดาษเฉลยของครู | หน้าพิมพ์และดาวน์โหลด PDF |
| สแกนและตรวจ | รับค่าการฝนจากมือถือแล้ว**คิดคะแนนซ้ำด้วยโค้ด** (server ชนะ), ข้อสงสัย (ฝนซ้ำ, ฝนไม่ชัด, ตัวเลขผิดรูป) เข้าคิวตรวจทาน, เลือกชุดเมื่ออ่านไม่ได้, "ครูอ่านรอยฝน", ตรวจใหม่ทั้งห้องด้วยโค้ด, ประกาศผลทั้งห้อง | **สแกนต่อเนื่องและให้คะแนนในเครื่อง** (OpenCV), สแกนกระดาษเฉลยเพื่อกรอกเฉลย, หน้าตรวจทานรอยฝน, หน้าเลือกชุด, ผลของนักเรียน (เห็นเฉลยเมื่อครูเปิด) |
| **วิเคราะห์ (build 6)** | `GET /exams/{id}/option-analysis`: จำนวนและร้อยละที่เลือกแต่ละตัวเลือก**ต่อข้อต้นฉบับรวมทุกชุด**, ไม่ตอบ, ฝนหลายตัว, กลุ่มสูง/ต่ำ 27%, ป้าย "ตัวลวงที่ไม่มีใครเลือก" และ "ตัวลวงที่กลุ่มสูงเลือกมากกว่ากลุ่มต่ำ" (เมื่อเผยแพร่ ≥ 20 คน); **item analysis จัดกลุ่ม 27% ตามคะแนนรวมที่ใช้จริง** (`effectiveTotal()`, รวมการบ้าน) | หน้าวิเคราะห์ตัวเลือกอยู่ในส่วน app ของ build 6 |
| ตัวชี้วัดและ mastery (build 6) | ข้อของข้อสอบผูกตัวชี้วัด, AI เสนอจากแผน หรือ**จากตัวชี้วัดทั้งรายวิชา**เมื่อข้อสอบไม่ผูกแผน (ส่งข้อความตัวเลือกไปด้วย), เสนอเองตอนอนุมัติเฉลย, ผลที่เผยแพร่เข้า mastery เป็น `source = exam` (α = 0.30 เท่าการบ้าน) จึงเข้ากราฟ spider ทันที | ใช้หน้า "จับคู่ตัวชี้วัด" เดิม |

### ประหยัด token (DESIGN §21)

อ่านเอกสารครั้งเดียว, ตัดสินช่องว่างและตัวเลขที่ CNN มั่นใจโดยไม่เรียก AI (ปิดไว้จนกว่า calibrate กับลายมือจริง), หนึ่ง call ต่อหน้า, media resolution ตามงาน, thinking level และเพดาน output ต่องาน, ใช้คำอธิบายซ้ำเมื่อคำตอบผิดแบบเดียวกัน, `ai_calls` บันทึก token แยกตามฟีเจอร์, ย่อภาพ crop บนมือถือเหลือ 768 px และ **calibration harness** (`eduvision:calibrate-gemini`)

## 7. ข้อที่ยังต้องตัดสินใจ

- **limiter `google-signin` 10 ครั้ง/นาที ต่อ IP**: ทั้งห้องกด Google พร้อมกันจากเครือข่ายโรงเรียนเดียว (NAT) จะชน limit ควรลองของจริงก่อนเพิ่ม (DESIGN §24.22)
- **ช่องว่างที่ยอมรับไว้ในแอป** (DESIGN §24.21, §24.25, §24.28): ครูประจำชั้นยังไม่มีสมุดคะแนนแบบอ่านอย่างเดียวของรายวิชาครูคนอื่น, ยังเลือก `app_course_id` จากการ์ด Classroom ของห้องไม่ได้, และหน้าของการบ้าน/ข้อสอบในห้องเก่ายังแสดงปุ่มเขียน (server ตอบ 409 พร้อมข้อความไทย) ควรตัดสินว่าจะทำก่อนใช้จริงหรือไม่

- **เคสแสดงวิธีทำที่คำตอบใกล้เคียง** (เช่น 38 แทน 36) ยังได้ระดับ "มั่นใจ" และอนุมัติแบบกลุ่มได้ ข้อเสนอ: บังคับอย่างน้อยระดับ "ควรดู" (DESIGN §11.8)
- **ระดับ media resolution**: ผ่านเกณฑ์ที่ `low` กับภาพสังเคราะห์ แต่ควรรอผลกับลายมือจริง (หัวข้อ 6 ข้อ 6) ก่อนลด
